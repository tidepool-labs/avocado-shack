## How to read the table

- **S** is the Hass writer state, **M** the private media root (`media/…` in backup), **H** the host root, **B** one output directory. **B1** = `hass/statebackup.py:38–55,135–150,196–219,229–249`: exact file allowlist, no arbitrary recursion, whole SQLite DB snapshots (inbox first if present). A regular unknown entry inside an inspected state directory can **refuse the entire backup**, not just be omitted. A separate root is not scanned. A symlink standing in for an otherwise allowed file or the intentionally skipped correspondence folder isn't a regular allowed entry.
- **B2** = `hass/statebackup.py:152–218,231–247`: explicit `--media` must pass the strict root scan; an existing configured `settings.mediaRoot` is also selected if `settings.npp is True`. The configured root uses the looser top-level scan when distinct from the explicit root (including when no explicit root was passed). If they are the same, the explicit strict scan applies. An unsettled original/sidecar pair prevents completion; unrelated top-level names in a distinct configured NPP root are ignored, not copied. `hass/statebackup.py:473–479` disables NPP on restore without a media restore target or with open jobs missing required originals. Thus a SQLite file in a backup does not by itself prove those jobs can resume.
- **R1** = `hass/retention.py:38–52,130–159`; **R2** = `hass/retention.py:61–115,160–167`. These are reporting selectors, not cleanup. They are narrower than the set of tables/files captured by B1/B2. **H1** = `hass/host.py:138,438–452,575`; `hass/publish_live.py:152–157`; `deploy/hass/hass-worker.service:10`. **U** = `deploy/hass/hass-backup.service:4–10`, `deploy/hass/hass-backup.timer:4–9`: the committed unit calls `create` with `--state` and `--out`, without `--media`; the persistent timer schedules daily at 03:30 America/Los_Angeles. It does not rotate old backups. The separate runtime-release caller can start that same service (`hass/runtime_release.py:213–214`); this is source wiring, not a claim that the timer is installed, enabled or succeeding.

## Written but not named by either selector

The high-impact cases are the publication books (journals and anchor) and stage timings: publishing writes to the host root, and both the host and the Mac write timing there or in the Mac spool (see table). The publication reader derives the last site head and push history from the anchor plus journals (`hass/release_journal.py:135–161,196–217`); those books are not equivalent to the editor's short-lived `S/journal/`, nor reconstructed by the writer-HEAD bundle. The host relay and arrivals and the catalog's community DB are similarly separate. Checked B1's top-level and child allowlists, B2's media roots, the unit's explicit arguments and R1/R2's SQL/file selectors. None names these paths.

The intake and maker logs and the other Clover stores/reports are a different kind of gap: the writers above put them **inside** the writer state (or below `clover/`), but no backup allowlist entry or H21 selector covers those paths. Their presence in the inspected layout can trigger a refusal (B1), including when `clover/reports/` is present as an unlisted child. Conversely, NPP receipts, cards and the NPP tables are **not** missing from both: B2 admits the named artifacts and B1 snapshots the conversation DB. H21 does not count them. Correspondence is explicitly named and skipped by B1 and has a separate pruner; it is not an unknown-entry gap.

## Documented options versus actual defaults

- **Comparison windows, not an expiry:** `docs/hass/RETENTION-OPTIONS.md:5` says “7, 30 and 90 days are three comparison points, not chosen defaults and not limits that anything enforces.” The CLI says `rep.add_argument("--days", required=True, type=_days)` and sets `MAX_DAYS = 36500` (`hass/retention.py:25,169–182`); `cutoff = (now or datetime.now(timezone.utc)) - timedelta(days=days)` and `doc["deletes"] = 0` (`hass/retention.py:132,166`). The options apply to what-if counts, not the independent 90-day correspondence or backlog cleanup, the 24-hour closed-request cleanup or the other rules in the table. An inbox row can stay counted after its payload is cleared, and an outbox row can be dropped for a send/batch outcome; neither is an enforced age window. The docs' “No deletion step enforces a retention period on any class it counts” (`docs/hass/RETENTION-OPTIONS.md:11`) should be read at the class level, not as a claim that no underlying store ever removes fields, rows or uncounted companion data.
- **Transcript exception:** “This class is kept indefinitely, with no deletion code; the open comparisons below do not apply to it” (`docs/hass/RETENTION-OPTIONS.md:3`; table at line 26). Code uses `INSERT OR IGNORE INTO events` (`hass/transcript.py:28–33`), snapshots the DB (B1), and H21 does not query it (R1). This is a separate class from `conversation.sqlite3:messages`.
- **Backup schedule versus lifespan:** “How often are backups made, how long is the recovery window, how many verified recovery points are kept” (`docs/hass/RETENTION-OPTIONS.md:70`). U answers the checked-in schedule, not the live schedule, restore validity or lifespan. `create` names/stages one directory and does not expire previous ones (B1 and `hass/statebackup.py:220–266,570–595`); `_backups` just tallies complete/incomplete from the name and presence of a regular manifest (R2). Counting a backup as complete doesn't verify it (`docs/hass/RETENTION-OPTIONS.md:18`; `hass/statebackup.py:336–382`).
- **Photo coverage:** “The backup lists photo originals and their description files only. When a media folder is given, a backup is refused if that folder holds a web-copy folder beside the originals” (`docs/hass/RETENTION-OPTIONS.md:53`; backup inventory at line 36). The explicit-root `web/` refusal still holds. The word “only” misses NPP cards and receipts, and the explicit-root wording doesn't describe configured NPP discovery that can select originals and artifacts while ignoring `web/` (B2). Separately, the doc's “Only finished `.png` files directly in the screenshots folder are counted” (line 33) is accurate for R2; it's not the full backup picture rule, which includes digest-named fallback JPEGs.

## Ranked gaps

1. **Whole-backup refusal from newer writers inside `S`.** An applied intake log or a non-cache Clover child, for example, can prevent a fresh recovery point rather than merely leave out that one artifact (B1 and writer rows above). This is a source risk, not an observed failed job.
2. **Selective recovery misses state needed beyond the writer checkout.** Publication books, host queues and the catalog community DB are independent of the committed content bundle; NPP restart also depends on the presence of referenced originals (H1, B1/B2 and separate-store rows above). This audit makes no claim about other backup tools.
3. **The options page is not a complete map of independent retention.** Its comparison windows are not live defaults; narrow on-write cleanup and size rollover already exist on other kinds. The timer supplies a schedule, not a backup lifetime, and the media paragraph omits the implicit NPP branch (U, B2 and the relevant table rows).

One bounded follow-up (estimate **60–90 minutes**, not implemented): clarify `docs/hass/RETENTION-OPTIONS.md` (backup inventory, media scope and cadence vs. lifespan) and extend `hass/tests/test_retention_options_doc.py` to check the two distinct media paths and that 7/30/90 are described only as comparisons. Offline check: `python3 -B -m unittest hass.tests.test_retention_options_doc`. No behavior change, new backup inclusion, retention choice or live procedure is proposed.

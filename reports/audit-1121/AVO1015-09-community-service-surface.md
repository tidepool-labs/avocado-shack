## R1. Routes and request limits

The script binds to `127.0.0.1` (default port 3101) and initializes the database on startup. The dispatcher matches the URL path, not query parameters, for API routes and the `/hike` alias. The API paths listed below match exactly (no trailing-slash alias). There is no application request-rate limit; the party-size bound, event capacity, duplicate handling and 10-second SQLite connection timeout are not rate limits. (`community-server.py:7–15,52–58,67–131,133–138`)

| --- | --- | --- | --- |

Opens SQLite via `connect()` (can create the directory/schema and attempts to set DB permissions). - **Shared POST checks, in order:** `Host` must be `localhost` or `127.0.0.1` with the actual server port. A nonempty `Origin` must be one of those exact HTTP origins with the port; absent or empty is allowed. Failure at either gate gives 403. The declared `Content-Length` must be an integer of 1–8192 bytes (missing defaults to 0; missing or out of range gives 413, non-integer gives 400). The parsed media type must be `application/json` (415 otherwise). The body must decode as JSON and its top level must be an object (400 otherwise). Form errors are 400; a caught POST SQLite error returns 503. API replies use JSON, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. (`community-server.py:62–66,80–92,125–131`)
- **Shared email rule:** must be a string; strip surrounding whitespace and lowercase first. Reject remaining ASCII controls (U+0000–U+001F and U+007F) and strings over 254 characters. Full match against `[^\s@]+@[^\s@]+\.[^\s@]+`: nonempty parts, one `@`, a dot in the domain part, no whitespace. No mailbox or delivery check. (`community-server.py:1,37–44,94,101,106,124`)
- **Capacity vs. opening:** GET reports `confirmedGuests` as the sum of party sizes, default 0; `remaining` is the positive integer cap minus that total, floored at zero, or null without such a cap. `rsvpOpen` checks schedule, meeting point and the enable setting, not available capacity. Both capacity checks use Python `isinstance(capacity, int)` (so a configured Boolean `true` acts as 1); that is distinct from strict integer checking for submitted `partySize`. (`community-server.py:46–50,71–79,110–111,118–121`)

## R2. What is stored and what comes back

SQLite defaults to the repository-relative `community-data/community.sqlite3`, outside the served directory; `AVOSHACK_COMMUNITY_DB` overrides it. `connect()` attempts mode `0600` and ignores a chmod failure. The handler suppresses its access log (`log_message` is `pass`). Personal-data labels here distinguish direct identifiers and information linked to a participant; they do not decide policy or retention. (`community-server.py:7–26,52–61`; `AGENTS.md:13–16`)

| SQLite field | Value and personal-data relationship | Returned by a route? |
| --- | --- | --- |
| `subscriptions.email` | Normalized address, primary key; direct identifier. (`community-server.py:16–18,37–44,94–100`) | No; fixed signup reply **A**. |
| `subscriptions.newsletter` | Integer opt-in flag (0/1); preference linked to email. (`community-server.py:17,94–100`) | No; **A**. |
| `subscriptions.hikes` | Integer opt-in flag (0/1); preference linked to email. (`community-server.py:17,94–100`) | No; **A**. |
| `subscriptions.created_at` | UTC ISO timestamp of first signup; linked to email. (`community-server.py:18,31–32,96–100`) | No; **A**. |
| `subscriptions.updated_at` | UTC ISO timestamp of last accepted signup, even if flags do not change; linked to email. (`community-server.py:18,31–32,96–100`) | No; **A**. |
| `subscriptions.consent_version` | Fixed `local-setup-v1` at insert, unchanged on merge; not identifying alone, attached to the consent record. (`community-server.py:18,98–100`) | No; **A**. |
| `rsvps.id` | SQLite-assigned integer primary key; internal row identifier linked to a participant. (`community-server.py:19–22,122`) | No; **B, C**. |
| `rsvps.event_id` | Configured event ID; not personal alone, but the row links an event to a person. Part of the unique event/email pair. (`community-server.py:19–22,103,115,122`) | Calendar returns the configured ID (not the RSVP row's ID field); used to group totals. Duplicate indication relates to the submitted event/email pair. **B, C**. |
| `rsvps.email` | Normalized address; direct identifier, part of the unique pair. (`community-server.py:20–22,37–44,106,115,122`) | Not echoed; duplicate indication only. **B, C**. |
| `rsvps.name` | Trimmed submitted name; direct identifier. (`community-server.py:20,106–109,122`) | No; **B, C**. |
| `rsvps.party_size` | Group size linked to the RSVP; DB constraint 1–6. (`community-server.py:21,110–111,122`) | No row value; contributes to aggregate `confirmedGuests` and `remaining`. **B, C**. |
| `rsvps.created_at` | UTC ISO timestamp of booking; linked to the RSVP. (`community-server.py:21,31–32,122`) | No; **B, C**. |

- **A — Signup reply:** `{'saved':True,'emailSent':False,'message':'Saved to the local signup list. Email delivery is not connected yet.'}` (`community-server.py:101`). There is no subscription read route (`community-server.py:67–79,93–125`).
- **B — RSVP replies:** the duplicate check runs `SELECT party_size FROM rsvps WHERE event_id=? AND email=?` but returns `'alreadyRegistered':True` rather than the selected value. Both RSVP 200 replies send `'saved':True,'emailSent':False` with fixed messages; the capacity/closed and validation errors do not return a row either. (`community-server.py:103–131`)
- **C — Calendar projection:** `SELECT event_id,SUM(party_size) seats FROM rsvps GROUP BY event_id`; event details come from `e=dict(item)`, and `e['confirmedGuests']=int(counts.get(e['id'],0))` is derived, as is `remaining`. The reply selects `clubName`, `emailConnected` (hard-coded false), `acceptsSubmissions` (hard-coded true), `events`, `routeIdeas`, and `showSamples` only when explicitly false. It copies configured event and route-idea objects, not individual RSVP records. (`community-server.py:67–79`)
- **Separate file store:** The checked-in `community.json` is read-only to the service. `AVOSHACK_COMMUNITY_CONFIG` overrides what the API reads. The sample has an empty `/events` array. `/clubName` and `/emailConnected` are club settings, not participant data; the API reads `clubName` but returns a fixed false for `emailConnected`. `/organizer` and `/intendedSender` are identity/contact fields, not submissions; the API does not select them. `/routeIdeas` records contain non-participant trail descriptors (`id`, `title`, `place`, `character`, `distance`, `difficulty`, `elevation`, `elevationLabel`, `duration`, `routeType`, `terrain`, `description`), attribution (`sourceUrl`, `sourceName`) and display settings (`status`, `rsvpEnabled`); the API passes these records through. Inherited `GET /community.json` can return the checked-in file as a static asset, independently of the config override. Neither form writes this file. This is the local server, not a published export. (`community.json` pointers above and `/routeIdeas/0`–`/routeIdeas/2`; `community-server.py:7–9,28–29,52–58,67–79,93–124`; `README.md:28`)

## R3. Where the two consents can change

| Source | Newsletter consent | Hiking-updates consent |
| --- | --- | --- |
| `POST /api/community/subscriptions` | Can set `newsletter` to 1. | Can set `hikes` to 1. **Both can be set by one request** if both choices are true. The SQL uses `MAX(subscriptions.newsletter,excluded.newsletter)` and `MAX(subscriptions.hikes,excluded.hikes)` separately, so an off or omitted choice does not revoke a previous yes. (`community-server.py:93–101`) |
| `POST /api/community/rsvps`; GET/HEAD; unmatched paths or methods | Cannot set it. | Cannot set it. The RSVP handler only inserts into `rsvps`, even if given extra consent keys; other handlers have no subscription write. (`community-server.py:52–79,102–131`) |
| Hike-page `#hike-updates` | Copy: “Hiking updates only; Michael’s newsletter has its own signup.” The newsletter link goes to `/#newsletter`; this form sends `newsletter:false`. | Button: “Keep me on the trail list ↗”. This form sends `hikes:true`. (`hike/index.html:24`; `community.js:173`) |
| Home `#community-newsletter` linked from hike page | Button: “Send me Michael’s newsletter ↗”. This form sends `newsletter:true`. | Separate, initially unchecked choice: “Also send me North Coast Hiking Club updates.” The payload uses the checkbox’s checked state. (`index.html:28`; `community.js:174`) |
| Hike RSVP dialog / sample RSVP | No opt-in in either; the real dialog says “Your RSVP goes on the club’s list. No confirmation email is sent.” | The real payload has event ID, name, email and party size only; the sample says “Sample RSVP · nothing is sent or saved.” and only resets the form and updates the page. (`community.js:51,135–136,178`) |

The two signup forms and the real RSVP send only if the page’s API probe finds `acceptsSubmissions:true`; no-service mode skips the API request, falls back to static data for display and disables the signup forms when the probe settles. (`community.js:138–177`)

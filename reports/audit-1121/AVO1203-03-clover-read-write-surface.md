## R1. Functions and guards

In the tables, bare filenames are under `hass/clover/`. A *code check* below means the engine looks up the row with `WHERE code=? AND sender=? AND chat=?` and refuses on `if not text.startswith("yes ") or row is None or row["status"] != "draft" or row["expires"] <= self.clock():` (`apply.py:55–57`, `dryrun.py:89–93`). A *live gate* means `if not self.config.writes_allowed:`, the persisted pause lookup `if db.execute("SELECT 1 FROM meta WHERE k='paused'").fetchone():`, and, unless undo, `if writes_today >= config.daily_write_cap:` (`apply.py:39–46`, `drafts.py:85–88`). `writes_allowed` is `self.live_approved and self.writes and bool(self.write_token_file) and self.write_token_file != self.token_file` (`config.py:45–48`); the live client factory also checks `if not config.writes_allowed:` (`dryrun.py:39–54`). These settings checks are not per-draft approval.

## R3. Do the docs match?

- **`docs/hass/CLOVER.md:432–433`:** “2 Direction: read and, by approved draft, write items and stock only.” At 471: “Original private `yes <code>` only: groups, edits, reactions and bare yes refuse.” This matches normal fresh till apply: the engine gates the approved draft and the client restricts POST/PUT. It does **not** describe every local write or place authorization in the client/transport. The wired shelf follow-up can release the already selected till code after the shelf check question, not originate an unbound till approval (`hass/conversation.py:1334–1341,1975–1986`). Undo really does create a separate draft (`apply.py:132–141`, `chat.py:69–76`). “Recovery only reads: it never retries a write” (485–487) holds for the remote side of intent recovery, not local settlement; the newer durable job flow (305) can execute a still-draft approved job for the first time (`approvals.py:68–79`). The earlier “no write path exists yet” (216) is historical, not a current source inventory; the same doc now describes the write switch (495–511), and `hass/host.py:476–503` wires the selected engine. Installed mode was not checked.
- **`docs/hass/POS.md:3–6`:** “from the **private cache only**” and “nothing is sent anywhere, no token is loaded, no network call is made.” At 20: “Links are made with `link suggest` and the owner's `link` commands”. At 45–46 it says report “reads the cache and the local products and links” and “writes into `<state>/clover/reports/`”. POS does **not** state an all-writes-require-yes rule. Its read-only-till/private-output distinction matches `cli.py:182–218` and `pos.py:132–169`; it is not evidence about which gates cover live inventory writes. The owner's link command is distinct from approving a Clover inventory change (`chat.py:230–259`).

## R4. Ranked gaps and one possible follow-up

1. **Rehearsal can settle but fail at the chat outcome boundary.** The `dry-run` status has no `NOT_DONE` entry; `approvals.recover` can later treat it as held, not a successful rehearsal (`dryrun.py:107–108`, `chat.py:36–37,338–348`, `approvals.py:71–79`). This is a static code finding, not a live incident.
2. **Approval lives at the engine and its callers, not at the sending boundary.** `write` and transport have other protections, but no approval check; standalone bundle helpers synthesize engine approval calls after their own outer checks (`client.py:202–210,259–275`, `transport.py:31–43`, `bundle.py:136–174`). This is a caller contract, not evidence of unauthorized use in deployment.
3. **“Read-only” and “dry-run” do not mean “no local writes.”** Cache writes, initialization before code validity, private output/pruning and recovery settlement are real local effects. Neither the standalone saga nor mutation read-back has a faithful dry counterpart (R1–R3).

**One possible unit, not implemented (estimate: 90–110 minutes):** recognize successful rehearsal in `hass/clover/chat.py` and `hass/clover/approvals.py` and extend `hass/tests/test_till_yes_durable.py`. Offline test: in a disposable journal/conversation with fixture reads, submit a synthetic owner approval and assert one rehearsal outcome, job done, dry receipt present, zero HTTP writes and zero site apply. Also interrupt after rehearsal settlement but before the outcome transaction commits; restart and replay the same inbound ID. Require the same single outcome without a second receipt or execution. The baseline single-pass failure is the non-applied result lookup raising after settlement; the interrupted case would report held instead of rehearsed. The engine-only tests assert the `dry-run` status but do not exercise those mappings (`hass/tests/test_clover_dryrun.py:94–145`); reuse the durable test's outcome/restart fixture (`hass/tests/test_till_yes_durable.py:63–133`). No policy, mode, cap, timer or live-enable change proposed.

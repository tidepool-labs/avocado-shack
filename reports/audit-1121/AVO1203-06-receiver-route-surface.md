## R1. Routes, fields, limits and authentication

**Common gate.** The socket peer must match a configured `allowedPeers` IP (403 first); then the method and raw path must match the table literally (404 for an allowed peer using GET, PUT, DELETE, HEAD, PATCH, OPTIONS or a different path, including a query or trailing slash). Methods with no handler are left to the HTTP library. No separate health or upload route is registered. The handler needs digit-only `Content-Length` (411 otherwise), checks the ceiling before reading (413 above it), and reads JSON bytes; it does not check request `Content-Type` or implement chunked-body decoding. It has a 10-second socket timeout, not an end-to-end processing deadline (`hass/host.py:29–35,92–117,136–138,208–245,274–281`).

**Common envelope.** Exact keys `v`, `ts`, `nonce`, `body`, `mac`; `v` and epoch-second `ts` are integers; nonce is lower-case hex for at least 16 bytes; MAC is 64 lower-case hex characters. Repeated keys at any depth and non-JSON numeric constants are refused. HMAC-SHA256, a timestamp no more than 300 seconds away in either direction, and an unused nonce are required. V1 uses the shared key; v2 uses a separately derived control key. V2 validation records the nonce before route-specific dispatch; a route-level rejection or rate limit after that step does not undo it (`hass/receiver.py:59–65,103–128`, `hass/bridge.py:23–27,103–143`, `hass/relay.py:56–57,143–170`, `hass/host.py:243–271`).

|---|---|---|---|

Intake does not allow-list `kind` values or separately cap text or attachment count; worker rules are separate (`hass/conversation.py:193–201,1257–1279,2032–2035,2338–2341`, `hass/bridge.py:25–27,128–143`, `hass/receiver.py:119–123`, `hass/inbox.py:45–59`). | 64 KiB; peer + v1. `Receiver._intake` also measures raw string/bytes inputs before JSON parsing, but not already-decoded objects (`hass/host.py:29,226–242`, `hass/receiver.py:27,103–118,147–154`). | `Receiver.accept` → `bridge.unseal` → `Inbox.enqueue`. HTTP 200 with only `result`: `queued`, `history`, `duplicate`, or `rejected`; 200 is not a receipt for completed processing (`hass/host.py:241–242`, `hass/receiver.py:116–135`, `hass/inbox.py:141–155`). |

| `POST /v1/photo` — bytes or refusal | `op: photo`, `guid`, `idx`, `count`, `sha256`, `b64`; or `op: photo-refused`, `guid`, `idx`, `count`, `code`. `guid` is a string of 1–200 code points without control or surrogate characters, not `.` or `..`; `idx` and `count` are ints with `0 ≤ idx < count ≤ 4`. `sha256` is lower-case hex and must match decoded `b64`. Refusal codes: `too-large`, `unsupported-type`, `fetch-failed`, `size-mismatch`, `empty`, `http-error`, `transport-error`, `not-json`, `shape`, `attachment-count`, `password-unreadable` (`hass/relay.py:102–125`, `hass/bridge_photos.py:26,57–61`, `hass/media.py:31–35`). | 12 MiB JSON; peer + v2; `photos` must be enabled (separate from outbound `pictures`). Strict base64 for **1 byte through 8 MiB** of decoded data, encoded length ≤ `4 * ceil(8 MiB / 3)`. The HTTP store checks length/digest, not image type. Server-wide limit is 8 accepted-for-attempt posts in the most recent 60 seconds, including refusals and attempts that then fail a store consistency check; next is 429 (`hass/host.py:31–34,109,137–138,234–256,275–281`, `hass/relay.py:15,110–125`, `hass/relay_photos.py:48–63`). | `RelayPhotos.put` → signed `photo-ok` with `guid` and `idx`. The control decoder knows response shapes as well; the host rejects operations not listed for that path with HTTP 400. The Mac-side fetcher's separate 20 MiB source-download cap and JPEG/PNG pass-through or conversion are **not** limits enforced by the HTTP receiver. The worker separately checks JPEG/PNG content before keeping originals (`hass/host.py:243–271`, `hass/relay.py:122–146`, `hass/bridge_photos.py:119–121,137–149`, `mac/hass_forwarder.py:327–375`, `hass/media.py:31–35,273–282`, `hass/conversation.py:2349–2366`).

## R2. Where accepted items go

`<state>` means the configured state directory; `<host-dir>` means the directory containing the host configuration. These are placeholders, not installed paths (`hass/host.py:106–109,135–138,574–584`).

| Route/action | Stored form and directory pattern | Next reader or consumer |
|---|---|---|
| Inbound message | `<state>/inbox.sqlite3`: pending `inbound` row with JSON `Inbound` payload, provider ID and clocks; nonce in `nonces` commits with the row. Pre-start history has ID and timestamps but no payload; a duplicate does not requeue. A successful drain marks done and clears the payload (`hass/receiver.py:116–135`, `hass/inbox.py:72–104,141–171`). Newly queued messages also get a hashed-ID stage record in `<host-dir>/stages.jsonl` (diagnostic, not a second payload store; `hass/receiver.py:127–130`, `hass/host.py:574–582`, `hass/stagelog.py:23–42,54–73`). | Separate `host.Worker` drains `Inbox` in received-time then ID order and calls `Receiver.handle` → `Conversation.handle`. The downstream sender/chat, echo and kind checks are not HTTP authentication (`hass/host.py:363–368,502–504,576–584`, `hass/inbox.py:157–204`, `hass/receiver.py:86–97,137–145`, `hass/conversation.py:1078–1088,1257–1279`). |
| Photo bytes / refusal | `<host-dir>/photos.sqlite3`: `photo_in` stores a BLOB or refusal code, with count, index and time; `photo_receipt` tracks repeats by `(guid, idx)` without retaining the BLOB. No per-photo file at HTTP intake. Receipts prevent reinsertion on identical retry; reconcile clears arrivals for completed inbox items, and expiry prunes old rows that are not protected by pending inbox items (`hass/host.py:275–281`, `hass/relay_photos.py:23–63,68–98`). | Worker-side `Conversation._photo` calls `RelayPhotos.fetch_for_inbox` using the message ID and count; waits/retries for missing parts or handles a recorded refusal. Only checked image bytes become `<mediaRoot>/originals/<first-two-sha-hex>/<sha256>.jpg` or `.png` plus `<sha256>.json` sidecar. The conversation can hand stored hashes to its listing flow; when requested, `media.web_copy` reads originals and writes a filtered image under `<mediaRoot>/web/<first-two-sha-hex>/` (`hass/host.py:450–461`, `hass/conversation.py:2338–2371`, `hass/media.py:183–200,391–418`). |
| Relay pull | No stored copy of the request. Reads `<host-dir>/relay.sqlite3`: reply rows and shot descriptors; writes handoff time and `meta.last_pull_at`. Oldest eligible unacknowledged rows first; previously handed rows become eligible after more than 60 seconds, and card rows require receipt capability (`hass/relay.py:13,173–184,218–239`). | `mac/hass_forwarder.py` verifies and consumes `replies`; its `<spoolDir>/spool.sqlite3` tracks text/shot delivery and card results. Text send uses the `bridge` adapter; picture retrieval is separate (`mac/hass_forwarder.py:142,478–483,493–570`, `hass/bridge.py:175–189,194–215`). |
| Relay ack | Updates `relay.sqlite3` acknowledgement state and clears acknowledged picture BLOBs. A receipt updates a handed card, confirming `sent` only when the digest matches the queued card and its stored shot; legacy ack can leave the card unconfirmed. Unknown/already-acked IDs do not create a new reply row (`hass/relay.py:241–282`). | Later `RelayStore.pull` / `picture` exclude acked rows; `receipt_for` reads the card state by outbox ID. Forwarder receives `acked`; that echo is separate from the stored confirmation (`hass/relay.py:212–228,278–282,350–351`, `hass/host.py:259–262`, `mac/hass_forwarder.py:565–570`). |
| Relay picture | Reads the PNG BLOB already in `relay.sqlite3` (worker reads eligible files under `<state>/screenshots/` and the relay stores up to two checked shots). No new host picture file or persisted download record; rate window is in memory (`hass/host.py:264–281,502–504`, `hass/relay.py:186–207,212–216,290–337`). | Mac forwarder checks digest, size and signature against the descriptor; consumes bytes for the attachment adapter and records delivery metadata in its spool. `bridge_attach.py` builds the outgoing multipart body in memory; it is not an inbound handler (`mac/hass_forwarder.py:485–511,513–538`, `hass/bridge_attach.py:13–38`). |
| Relay state | No stored pause-query item. `paused_flag` reads `<state>/conversation.sqlite3` and, when present, `<state>/inbox.sqlite3` read-only (`hass/host.py:160–204,263,582`). | Mac forwarder's `host_paused` reads the signed boolean; it is not a pause command (`mac/hass_forwarder.py:593–600`). |

All authenticated control requests that pass envelope validation, including `state`, also write replay metadata to the same `<state>/inbox.sqlite3` nonce table; that is separate from the route payloads and from the read-only pause check (`hass/host.py:243–245`, `hass/relay.py:157–170`, `hass/inbox.py:72–97`).

## R4. Ranked gaps

1. **Missing intake leg in the wiring diagram.** An operator using the diagram would see reply pictures but not the separate photo intake, its enable switch or its store (`docs/hass/BRIDGE_WIRING.md:15–22,46–50`; `hass/host.py:249–256,274–281`).
2. **No receiver contract in the wiring.** The JSON and decoded-byte limits are different, and the 64 KiB relay limit applies to requests, not the returned PNG. The transport accepts an envelope or stores bytes before the worker checks whether it can use them (`docs/hass/BRIDGE_WIRING.md:15–24`; `hass/host.py:234–271`; `hass/conversation.py:1263–1279,2338–2366`).
3. **Easy-to-misread acknowledgements.** `queued`, `photo-ok` and `acked` do not prove a draft, a valid image or confirmed delivery, respectively (`hass/receiver.py:132–145`; `hass/host.py:254–262`; `hass/relay.py:249–271`; `hass/conversation.py:2349–2366`).

No implementation unit is needed to finish this inventory. The gaps above can be addressed by documentation if separately commissioned; this report changes no route, limit, timer, approval or network rule.
